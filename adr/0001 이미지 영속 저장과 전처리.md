# ADR 0001: 이미지 영속 저장과 전처리

- 상태: 채택, 현재 구현을 기준으로 정리
- 기록일: 2026.10.25
- 범위: 업로드 이미지의 전처리, 로컬 저장, 중복 확인, 조회

## 배경

위스키 라벨 분석을 반복하면서 입력 이미지와 모델에 전달한 이미지를 다시 확인할 필요가 있다.
요청이 끝나면 사라지는 임시 파일만으로는 전처리 결과를 비교하거나 같은 입력을 재사용하기 어렵다.
원본을 보존하고 모델 입력용 이미지와 목록용 썸네일을 별도로 저장한다.

이 프로젝트는 로컬에서 실행하는 파일럿이다. 별도 데이터베이스 서버나 객체 저장소를 운영하지 않고 파일과 메타데이터를 함께 확인하는 구성을 선택한다.
이 문서는 기존 `IMAGE_PERSISTENCE_PLAN.md`를 대체하며 외부 프로젝트의 이슈를 읽지 않아도 결정과 구현 상태를 이해하도록 정리했다.

## 결정

### 1. 원본, 전처리본, 썸네일을 함께 저장한다

원본 bytes를 그대로 보존한다. 모델에는 전처리한 JPEG를 전달하고 저장 목록에는 썸네일을 사용한다.
같은 `file_id`로 세 이미지를 조회한다. 원본과 모델 입력을 비교할 수 있는 대신 이미지 한 장당 저장 공간이 늘어난다.

전처리 규격은 다음과 같다.

- 입력 형식: JPEG, PNG, WEBP, HEIC/HEIF
- 모델 입력: JPEG, 1024×1365, 흰색 배경, 품질 90
- 배치: 비율을 유지해 축소·확대한 뒤 여백을 채운다. 라벨이 잘리는 crop은 적용하지 않는다.
- 색상과 메타데이터: RGB 변환, ICC 프로필이 있으면 sRGB 변환을 시도하고 출력 이미지의 EXIF를 제거한다.
- 썸네일: 전처리본을 320×426 JPEG, 품질 90으로 축소한다.

1024×1365는 정확한 3:4가 아니라 근사 비율이다. 여러 병을 찍은 사진이나 가로 사진에서는 라벨이 작아질 수 있다.
전처리본의 메타데이터 제거는 원본에 적용하지 않는다. 저장된 원본에는 촬영 정보가 남을 수 있다.

근거: [전처리 프로필](../app/images/profiles.py), [이미지 전처리](../app/images/preprocess.py)

### 2. 원본 bytes의 SHA-256으로 중복을 확인한다

업로드한 원본의 SHA-256을 계산하고 기존 레코드가 있으면 저장된 `file_id`를 반환한다.
파일명과 무관하게 바이트가 완전히 같은 파일을 식별한다. EXIF나 인코딩만 달라도 다른 원본으로 취급한다.

전처리본의 SHA-256도 저장하지만 현재 중복 판정과 분석 결과 캐시에는 사용하지 않는다.
같은 이미지를 다시 분석하면 저장된 전처리본을 재사용하고 모델은 다시 호출한다.

근거: [파일 저장 서비스](../app/services/file_ingestion.py), [분석 서비스](../app/services/analyzer.py)

### 3. 파일은 PyFilesystem2, 메타데이터는 SQLite에 저장한다

PyFilesystem2의 `OSFS`로 로컬 파일을 저장하고 SQLAlchemy로 SQLite의 `files` 테이블을 관리한다.
이미지 bytes는 파일시스템에 두고 DB에는 경로, 해시, 크기, 형식, 처리 시각을 저장한다.
원본 SHA-256에는 unique 제약을 둔다.

기본 저장 위치는 `.data/`이고 `VISION_DATA_DIR`로 바꾼다. Docker에서는 `/data`를 볼륨으로 마운트한다.

```text
.data/
├── vision.db
└── objects/files/
    ├── original/YYYY/MM/DD/<file_id>.<확장자>
    ├── processed/YYYY/MM/DD/<file_id>.jpg
    └── thumbnails/YYYY/MM/DD/<file_id>.jpg
```

로컬 실행과 데이터 보관이 단순해진다. 현재 구현은 로컬 저장소만 지원하며 원격 객체 저장소 전환이나 다중 서버 운영은 구현 범위에 포함하지 않는다.
Docker 볼륨을 보존하지 않으면 컨테이너 삭제 시 데이터도 사라진다.

근거: [객체 저장소](../app/storage/object_store.py), [DB 모델](../app/db/models.py), [DB 생성](../app/db/session.py), [Dockerfile](../Dockerfile)

### 4. 파일 저장과 GPT 분석을 분리한다

`POST /api/files`는 저장과 전처리만 실행한다. GPT를 호출하지 않고 이미지 처리 결과를 확인할 수 있다.
`POST /api/analyze`와 `POST /api/analyze/stream`은 같은 저장 과정을 거친 뒤 전처리본으로 분석한다.

```text
업로드 → 원본 SHA-256 계산 → 기존 파일 조회
  ├── 중복: 기존 file_id와 전처리본 재사용
  └── 신규: 원본 저장 → 전처리 → 전처리본·썸네일 저장 → DB 저장
분석 요청인 경우 → 전처리본으로 GPT 호출
```

파일 조회는 `file_id` 기반 API로 제공한다.

- `GET /api/files`: 최근 목록, `limit` 1~100, 기본 40
- `GET /api/files/{file_id}`: 메타데이터와 이미지 URL
- `GET /api/files/{file_id}/{kind}`: `original`, `processed`, `thumbnail`

파일 레코드가 없으면 404, 레코드는 있으나 이미지 파일이 없으면 410을 반환한다.
목록 응답에 `next_cursor` 필드는 있지만 현재 값은 항상 `null`이며 cursor 페이지네이션은 구현하지 않았다.

근거: [API 라우터](../app/api/routes.py), [파일 저장 서비스](../app/services/file_ingestion.py), [파일 저장소](../app/repositories/files.py)

## 검토한 대안과 선택 이유

다음 비교는 현재 구현을 설명하기 위해 정리한 것으로 당시의 검토 기록을 뜻하지 않는다.

- 임시 파일만 사용: 저장 구조는 단순하지만 분석 이후 원본과 전처리본을 다시 조회할 수 없다.
- DB에 이미지 bytes 저장: 메타데이터와 함께 관리할 수 있지만 현재 파일 기반 조회와 디버깅 흐름에 맞춰 파일시스템 저장을 선택했다.
- 외부 DB와 객체 저장소 사용: 여러 서버가 저장소를 공유할 때 고려할 수 있으나 로컬 파일럿에서는 별도 서비스 운영을 추가하지 않는다.

## 현재 한계와 보류한 작업

다음 항목은 설계 방향이나 보완 후보이며 구현 완료를 뜻하지 않는다.

- 파일 저장과 DB 저장은 하나의 트랜잭션이 아니다. 이미지 검증이나 DB 저장이 실패하면 파일이 남을 수 있다.
- 원본 SHA-256의 unique 제약은 있으나 동시 업로드 시 insert 충돌을 기존 레코드 반환으로 복구하는 처리는 없다.
- 업로드 용량 제한, 사용자 인증, 사용자별 파일 접근 제어, 요청 제한은 없다. 공유 서버 운영 전에는 별도 설계가 필요하다.
- 이미지 삭제·보존 기간 정책과 실패 상태 이력은 구현하지 않았다. 정상 저장 레코드의 상태는 `processed_saved`다.
- 분석 결과 저장과 캐시, 토큰 사용량과 비용 집계는 구현하지 않았다.
- 분석 캐시를 추가한다면 전처리본 해시 외에 모델, 프롬프트·스키마 버전, 이미지 detail을 키에 포함해야 한다.
- 모델 식별 정확도는 파일 저장 테스트의 검증 범위에 포함하지 않는다.
